# 04. 技術選定と理由（案）

前提：バックエンドは Cloudflare、AIは Workers AI、ログインは Google のみ、モバイル向けWebアプリ。
注意：この調査環境からは Cloudflare の公式ドキュメントに直接アクセスできなかった。モデル名・機能名は実装を始める時点で公式カタログを確認して確定する。

## 全体構成

```
スマホのブラウザ（PWA）
   │  React SPA（静的ファイル）
   ▼
Cloudflare Workers（1つのWorkerが画面の配信とAPIの両方を担当）
   ├─ Hono（API）
   ├─ D1（データベース）……ユーザー、アイテム、コーデ、着た記録
   ├─ R2（画像の保存）……元の写真、切り抜き画像
   ├─ Images（背景切り抜き・サイズ変換）
   ├─ Queues（重い処理を裏で順番に実行）
   ├─ Workers AI（画像から属性を判定、提案の理由づけ、文章の意味の数値化）
   └─ KV（セッション、天気のキャッシュ）
外部：Google OAuth、Open-Meteo（天気）
```

## フロントエンド

| 技術 | 理由 |
|---|---|
| **TypeScript** | 画面とAPIで型を共有でき、AIが返すJSONの形も確かめられる |
| **React 19** | アニメーションのライブラリ（Motion）が一番充実している。共有要素の遷移やジェスチャーを作りやすい |
| **Vite** | ビルドが速い。Cloudflare公式のViteプラグインで、手元でもWorkersと同じ環境で動かせる |
| **TanStack Router** | URLやパラメータに型が付く。画面ごとにデータの先読みとスケルトンを決めやすい |
| **TanStack Query** | データの取得・キャッシュ・再取得をまとめて扱える。Suspenseと組み合わせてスケルトンを統一できる。先に画面を更新して後でサーバーに保存する作り（楽観的更新）が簡単 |
| **Motion（旧 Framer Motion）** | ばねの動き、`layoutId` による共有要素の遷移、ドラッグ、リスト要素の出入りを1つのライブラリで扱える。今回の「アニメーションを多用」に一番合う |
| **Tailwind CSS v4** | 色・角・ぼかしなどのデザインの値を一か所で決めて全体で使える。ガラスの見た目を部品として揃えやすい |
| **自作のガラス部品**（CSS `backdrop-filter` ＋ SVG フィルタ） | Liquid Glassの屈折はライブラリより自作の方が細かく調整でき、ブラウザごとの代替表示も決めやすい |
| **vite-plugin-pwa** | ホーム画面に追加、ショートカット（買う前チェック直行）、共有メニューからの受け取り（Web Share Target）、オフライン時の表示 |
| **カメラ：`getUserMedia`** | アプリ内のカメラで連続撮影するため。標準の写真選択（`<input type=file>`）は1枚ずつ画面を行き来するので、連続撮影では使わない（写真から選ぶ場合は使う） |
| **画像の前処理：ブラウザで縮小・圧縮** | 送る前に長い辺を1600px程度に縮めると、通信量が減って登録が速くなる |

## バックエンド

| 技術 | 理由 |
|---|---|
| **Cloudflare Workers（静的ファイル配信つき）** | 画面とAPIを1つにまとめて配信でき、同じドメインなのでCORSの設定やCookieの問題が起きない。Cloudflareは新しいプロジェクトにPagesよりWorkersを推奨している |
| **Hono** | Workersのために作られた軽いフレームワーク。型付きのクライアント（RPC）で、フロントからAPIを型付きで呼べる |
| **Zod** | 入力の検証と、AIが返したJSONの検証に使う |
| **D1 ＋ Drizzle ORM** | ユーザーとアイテムの関係データにはSQLが合う。Drizzleは型が付き、D1のマイグレーションに対応している |
| **R2** | 画像の保存。外への転送料金がかからない |
| **Cloudflare Images（背景切り抜き・サイズ変換）** | 切り抜き（`segment=foreground`、BiRefNetを使う機能として告知されている）と、一覧用の縮小を同じ仕組みで行える。自前で画像のAIを動かさなくて済む |
| **Queues** | 切り抜き → タグ付け → 似ている度合いの計算、を裏で順番に実行する。ユーザーは保存したらすぐ次を撮れる（登録1着3秒の前提） |
| **KV** | セッションの保存（読み込みが速い）と、天気のキャッシュ |
| **似ている度合い・組み合わせの計算：Worker内で計算** | 1人の手持ちは数百着なので、全件を比べてもすぐ終わる。ベクトルDB（Vectorize）は今は不要。規模が大きくなったら移す |

## AI（Workers AI）

| 用途 | モデル（候補） | 理由 |
|---|---|---|
| 画像から属性を判定 | `@cf/meta/llama-4-scout-17b-16e-instruct`（画像入力対応） | 画像と文章を両方扱える。JSONの形を指定して出力させ、Zodで確認する。確認できなかった値は「不明」とし、確認待ちで直してもらう |
| 提案の理由・3案の選び方 | 同上、または日本語に強い文章用モデル | 判定はルールで行い、AIは**言い回しと多様な選び方**だけを担当する。AIの結果がぶれても判定は変わらない |
| 説明文の意味の数値化 | `@cf/baai/bge-m3` | 多言語対応で、日本語の説明文も扱える。似ている度合いの補助に使う |
| 色 | AIではなく画素から計算 | 切り抜いた画像の画素から主色を出す方が正確でぶれない |

- **ルールとAIを分ける理由**：判定の根拠を数字で見せるため（`似ている 87%`）。AIだけに任せると理由が説明できず、同じ服でも答えが変わる。
- Workers AIが遅いときやエラーのときは、ルールで出せる部分（判定・＋N通り・似ている手持ち）を先に表示し、理由の文は後から入れる。

## ログイン

| 技術 | 理由 |
|---|---|
| **Arctic**（OAuthの小さなライブラリ） | Googleだけならこれで十分。Workersで動き、依存も少ない |
| **自前のセッション**（Cookie：HttpOnly・Secure・SameSite=Lax、保存先はKVとD1） | ログイン方法が1つなので、大きな認証ライブラリは必要ない。仕組みが見通せる |
| PKCE と state の確認 | OAuthの標準的な安全対策 |

## その他の外部サービス

| サービス | 理由 |
|---|---|
| **Open-Meteo** | APIキー不要、無料で天気予報が取れる。地域ごとにKVで1時間キャッシュする |

## 開発・公開

| 技術 | 理由 |
|---|---|
| **pnpm** | インストールが速く、容量を節約できる |
| **Biome** | 整形とLintが1つで済み、速い |
| **Vitest** | Viteと設定を共有できる。点数の計算や判定ルールのテストに使う |
| **Playwright** | スマホの画面サイズで操作のテストと、スクショの確認 |
| **GitHub Actions → `wrangler deploy`** | mainに入ったら自動で公開。D1のマイグレーションもここで実行する |

## リスクと対応

| リスク | 対応 |
|---|---|
| Images の切り抜きがベータ／料金がかかる | 変換した結果をR2に保存して、同じ変換を2回しない。使えない場合は切り抜きなしで登録し、表示側で背景を目立たなくする |
| AIのタグの精度 | 確認待ちで直せるようにする。直された結果をプロンプトの例として使う |
| `backdrop-filter` が重い（古いAndroid） | 端末の性能で判定し、ぼかしを弱める。スクロールする部分では重ねすぎない |
| SVG の屈折フィルタは Safari で効かない | Safari ではぼかしと縁の光だけで表現する |
| 店内の電波が弱い | 撮った写真をいったん端末に保存し、送れるようになったら送る。結果は届いた順に表示する |

## 次に必要なもの（実装を始める前）

- GitHub：この環境の GitHub トークンが無効になっている。リポジトリの作成と公開の前に、接続し直す必要がある。
- Cloudflare：アカウントID と APIトークン（Workers、D1、R2、KV、Queues、Images、Workers AI の権限）。
- Google Cloud：OAuth クライアントID とシークレット（リダイレクト先は公開URLの `/auth/google/callback`）。
